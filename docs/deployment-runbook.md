# 0.8.4 Project Deployment Runbook

`DEPLOYMENT.md` 是每个本地项目自己的部署/运维规范。0.8.4 的核心原则是：**Runbook 负责完整记录“这个项目可以怎样部署”，一键脚本只负责自动化“这个用户实际希望自动执行的那一部分”，而成熟后的 Agent 则负责把已验证自动化真正执行起来、自己检查结果，并和用户一起完成验收、诊断与恢复闭环。**

## 成熟路径

```text
阶段 1：生成并审查 DEPLOYMENT.md
          ↓
阶段 2：用户实际使用、调整并确认流程稳定
          ↓
阶段 3：询问用户真实操作习惯，确定自动化边界
          ↓
阶段 4：按确认后的边界生成并验证一键脚本
          ↓
阶段 5：Agent 自主执行 → 自检 → 用户验收 → 诊断/恢复 → 闭环
```

## 阶段 1：先形成可见 Runbook

第一次整理项目部署流程时，优先生成 `DEPLOYMENT.md`，不要直接把一键脚本作为最初形态。

Runbook 可以包含完整且真实的部署逻辑，也允许使用复合命令，包括变量、命令替换、管道、条件、循环、heredoc、多行 PowerShell/Bash block 等。这里强调的是**逻辑可见、可审查**，不是强行把所有命令拆成单行。

Agent 在整理 Runbook 前应先用只读方式核对真实本地项目和当前 session-bound SSH 环境，再修正历史命令中的路径、运行时、服务方式、端口、日志、版本、权限等信息。

Runbook 建议继续按 `LOCAL / TRANSFER / REMOTE / VERIFY / ROLLBACK` 组织，并写明每个逻辑步骤的用途、执行内容和成功条件。

## 阶段 2：由用户确认流程是否稳定

一次成功执行并不自动等于“流程已经成熟”。只有用户明确表示当前 `DEPLOYMENT.md` 已经经过实际使用、整体流程可以固定下来，才进入自动化讨论。

如果用户仍在调整任何步骤，就继续维护 Runbook，不主动把它脚本化。

## 阶段 3：自动化前必须做“使用习惯访谈”

**Runbook 中存在某条命令，不代表用户希望脚本执行这条命令。**

Runbook 是完整知识库；一键脚本只是其中一个自动化入口。用户完全可以把某些步骤保留为人工操作、交给其他工具或流程处理、从某个中间阶段开始，或者只在异常时参考某些章节。

因此，在生成脚本前，Agent 必须先对 Runbook 中相关逻辑步骤建立一份“自动化覆盖表”。每个步骤或步骤组至少要明确属于以下一种状态：

- `AUTOMATE`：纳入脚本自动执行；
- `KEEP MANUAL`：继续由用户人工处理；
- `EXTERNAL / HAND-OFF`：由 DSH 之外的其他工具或流程处理；
- `NOT IN NORMAL RUN`：保留在 Runbook 中，但不属于日常一键流程。

同时要确认各阶段之间的交接条件：

- 自动化从什么前提开始；
- 用户会在什么地方人工介入；
- 中间产物是否会被用户选择、调整或处理；
- 自动化在什么条件下可以继续；
- 哪些输入由用户提供；
- 哪些 checkpoint 必须暂停确认；
- 失败时停止、等待人工还是执行既定恢复策略；
- 哪些事情由外部工具或既有流程完成。

这些属于**用户使用偏好和操作习惯**，不能仅靠环境扫描推断。相反，能够通过只读检查直接确认的事实，不应该重新丢给用户回答。

## 不要假设“完整自动化”就是最优目标

最终脚本不需要覆盖整个 `DEPLOYMENT.md`。

如果用户真实习惯只希望自动化其中几个阶段，那么脚本就只覆盖这些阶段。其余步骤继续留在 Runbook 中作为人工流程、外部交接或恢复手册。

Agent 不应该因为某个步骤已经有现成命令，就默认把它塞进脚本；也不应该为了显得“自动化程度高”而消除用户刻意保留的人工操作。

**自动化边界由用户习惯决定，而不是由 Runbook 章节数量决定。**

## 生成脚本前先回显覆盖表

在真正写 `.ps1`、`.sh` 或其他一键入口之前，Agent 应先向用户回显拟定的自动化边界，例如：

```text
LOCAL        → KEEP MANUAL
TRANSFER     → AUTOMATE
REMOTE       → AUTOMATE
VERIFY       → AUTOMATE
ROLLBACK     → KEEP MANUAL

自动化开始条件：...
人工交接点：...
可变输入：...
失败策略：...
```

这只是格式示意，实际内容必须来自当前项目和用户真实习惯。用户确认或调整这份覆盖表之后，才能进入脚本生成阶段。

## 阶段 4：脚本来自“已验证 Runbook + 已确认使用习惯”

一键脚本应满足：

- 基于已经验证的 `DEPLOYMENT.md`；
- 只包含用户明确选择自动化的步骤；
- 复用已经验证过的真实命令，不重新发明另一套部署逻辑；
- 只把真正变化的值参数化；
- 保留用户要求的人工 checkpoint；
- 对人工或外部交接后的继续条件做显式检查；
- 明确失败处理和回滚边界；
- 不加入用户未要求的额外自动修改、删除、升级或清理动作。

脚本草案完成后，在保存或运行前仍应展示：

- 文件路径；
- 启动方式；
- 输入参数；
- 自动化覆盖哪些 Runbook 步骤；
- 哪些步骤保持人工或外部处理；
- 人工交接点；
- 失败与回滚策略；
- 完整脚本或足够完整的可审核 diff。

然后让用户选择继续修改、保存但不运行，或保存并试运行。脚本本身也应该经过至少一次真实使用和用户确认，才进入下一阶段。

## 阶段 5：Agent 自主执行并完成部署闭环

当 `DEPLOYMENT.md`、自动化覆盖边界和脚本入口都已经被用户实际验证后，Agent 的角色应从“给命令的人”升级成“执行和守护这次发布的人”。

以后用户正常提出“部署 / 发布 / 更新这个项目”时，只要本次所需输入已经明确，并且没有新增未审批的高风险动作，Agent 应主动完成已授权范围内的工作，而不是再次把脚本路径丢给用户让用户自己执行。

### 5.1 发布前：自己确认本次到底要发布什么

Agent 应先完成轻量 Preflight：

- 当前 Workspace 和目标 SSH 是否匹配；
- 自动化入口是否仍然与当前 Runbook 一致；
- 本次需要的版本、产物或其他输入是否已经存在；
- KEEP MANUAL / EXTERNAL 的前置交接是否已经满足；
- 远程服务、端口、磁盘和关键目录是否处于可部署状态。

如果本地项目存在可用的版本控制信息，还应尽量读取本次相关的 `status / diff / log / commit` 等证据，以便部署后告诉用户“这次主要改了哪些地方”。

如果无法可靠判断变更范围，就明确告诉用户无法确认，不要根据文件名或聊天上下文猜一份发布说明。

### 5.2 执行：由 Agent 自己运行已验证自动化

Agent 应在脚本设计时确定的执行平面上运行它：

- 本地入口就在 LOCAL Workspace 执行；
- 远程检查和远程操作继续限制在当前 session-bound SSH；
- 仍然尊重 `KEEP MANUAL` 和 `EXTERNAL / HAND-OFF`；
- 只在真正需要用户人工参与、缺少必要输入、或出现新的高风险操作时暂停。

“自主执行”不意味着扩大权限，也不意味着把原本保留给人的步骤偷偷自动化。

### 5.3 脚本成功不等于部署成功：必须独立自检

脚本退出码成功后，Agent 还应独立检查服务，而不是直接宣布上线完成。

应根据项目实际情况组合尽可能强的检查，例如：

- 进程 / service 状态；
- 监听端口；
- HTTP / Health Check；
- 当前部署版本或产物身份；
- 最近启动日志和关键错误日志；
- Runbook 中已有的安全 smoke test。

最终至少判断为：

```text
HEALTHY
WARNING
FAILED
```

### 5.4 把发布结果交接给用户做业务验收

技术自检通过后，Agent 应给用户一份简短、具体的“本次发布交接”：

- 本次部署了什么版本 / 产物；
- 当前服务是否健康；
- 是否存在 warning；
- 如果能够从 Git / Workspace 等证据中确认，本次主要修改了哪些模块或功能区域；
- 基于真实变更，建议用户重点测试哪些业务功能。

测试建议应尽量来自真实 change set 和项目结构，而不是每次都输出一模一样的通用测试清单。

Agent 的进程、端口、日志和 Health Check 只能证明“技术上看起来正常”，不能替代用户对业务功能的实际验收。此时应等待用户测试后的反馈。

### 5.5 用户反馈正常：结束本次发布

如果用户确认功能正常：

- 简短确认当前线上状态；
- 记录或提示本次部署闭环完成；
- 不再为了“多检查一点”继续修改服务器或运行有副作用的操作。

闭环到这里结束。

### 5.6 用户反馈异常：进入诊断闭环

如果用户反馈不正常，Agent 不应该立刻无脑重跑部署或直接改服务器。

优先按以下顺序排查：

1. 收集用户看到的具体现象、入口、请求和时间点；
2. 在安全范围内尝试复现；
3. 重新检查服务 / 进程 / 端口 / Health / 日志；
4. 对照本次实际部署版本和本地 change set；
5. 判断更像是发布/环境异常、应用代码回归，还是与本次发布无直接关系的问题；
6. 找到证据后再提出修复、继续排查或恢复建议。

### 5.7 风险变大时优先恢复，而不是执着于现场修复

如果服务已经明显不可用、影响生产、原因暂时不清楚，或者继续排查会扩大风险，应优先考虑恢复上一稳定状态。

默认行为不是偷偷自动回滚，而是把恢复方案清楚交给用户，例如说明：

- 回滚会恢复到什么版本 / 状态；
- 会执行哪些已验证命令或脚本；
- 是否会覆盖当前产物；
- 是否可能损失某些现场证据；
- 回滚完成后将执行哪些验证。

然后通过问题卡给用户类似选择：

```text
继续排查
给我回滚命令
由你执行回滚
```

如果 Runbook 和已验证脚本本身已经明确配置了自动回滚条件，并且用户之前明确批准自动回滚，则可按该策略执行；否则生产回滚应由用户明确选择。

### 5.8 回滚命令成功也不代表恢复完成

Agent 自己执行回滚后还必须重新检查：

- 当前运行版本；
- 服务 / 进程；
- 端口；
- Health Check；
- 最近日志。

只有旧版本重新处于健康状态，才能报告“已恢复”。

## 完整闭环

```text
确认本次发布内容
        ↓
Agent 执行已验证自动化
        ↓
Agent 独立检查服务状态
        ↓
总结变更 + 给出重点测试范围
        ↓
用户业务验收
        ↓
   ┌── 正常 ──→ 发布完成
   │
   └── 异常
        ↓
Agent 结合日志 / 服务状态 / change set 诊断
        ↓
继续修复 / 继续排查 / 回滚决策
        ↓
执行恢复后再次健康检查
        ↓
闭环
```

## DEPLOYMENT.md 始终保留

生成脚本、甚至进入 Agent 自主执行阶段后，`DEPLOYMENT.md` 仍然是人类可读的 source of truth，用于：

- 解释完整部署逻辑；
- 记录环境事实和前提；
- 说明脚本覆盖范围；
- 记录人工和外部交接点；
- 定义技术验证和业务验收边界；
- 提供脚本失败后的手工恢复路径；
- 在流程变化后指导脚本更新。

如果部署流程或用户操作习惯发生实质变化，旧脚本应视为可能过期。先更新/验证 Runbook 或自动化覆盖表，再更新脚本；脚本重新验证后，才恢复 Stage 5 的自主执行模式。

## 工具与 UX

- `deployment_runbook_status`：检查当前 Workspace Runbook 状态、hash 和 SSH 目标；
- `deployment_runbook_read`：读取项目自己的 `DEPLOYMENT.md`；
- `deployment_runbook_template`：生成 Runbook 基础结构；
- `deployment_runbook_write`：用户确认后创建/更新 Runbook；
- `ask_user_question`：适合用于 Runbook 审查、成熟度确认、自动化覆盖访谈、脚本确认、异常后的继续排查/回滚选择；
- Harness 原生 approval：用于真正高风险操作的单次授权。

## 最终原则

- **复合命令没问题，隐藏逻辑才是问题。**
- **一键脚本没问题，未经验证就直接一键化才是问题。**
- **Runbook 中有命令，不等于脚本必须执行它。**
- **自动化之前必须先问清楚用户真实的操作习惯。**
- **脚本经过验证后，模型应该自己执行，而不是继续把运维工作推回给用户。**
- **脚本成功不等于服务正常，部署后必须独立验证。**
- **模型负责技术自检，用户负责最终业务验收。**
- **用户反馈异常后要进入诊断闭环，而不是盲目重跑或盲目改线上。**
- **高风险或原因不明时优先给出恢复方案，并让用户决定是否由模型执行。**
- **回滚后同样必须验证恢复状态。**
- **DEPLOYMENT.md 始终保留为完整、可读、可恢复的来源。**
- 高风险操作继续受独立审批保护。

# 0.8.3 Project Deployment Runbook

`DEPLOYMENT.md` 是每个本地项目自己的部署/运维规范。0.8.3 的核心原则是：**Runbook 负责完整记录“这个项目可以怎样部署”，一键脚本只负责自动化“这个用户实际希望自动执行的那一部分”。**

这两者不能简单地一比一转换。

## 成熟路径

```text
阶段 1：生成并审查 DEPLOYMENT.md
          ↓
阶段 2：用户实际使用、调整并确认流程稳定
          ↓
阶段 3：询问用户真实的操作习惯，确定自动化边界
          ↓
阶段 4：按确认后的边界生成一键脚本
```

## 阶段 1：先形成可见 Runbook

第一次整理项目部署流程时，优先生成 `DEPLOYMENT.md`，不要直接把一键脚本作为最初形态。

Runbook 可以包含完整且真实的部署逻辑，也允许使用复合命令，包括变量、命令替换、管道、条件、循环、heredoc、多行 PowerShell/Bash block 等。这里强调的是**逻辑可见、可审查**，不是强行把所有命令拆成单行。

Agent 在整理 Runbook 前应先用只读方式核对真实本地项目和当前 session-bound SSH 环境，再修正历史命令中的路径、运行时、服务方式、端口、日志、版本、权限等信息。

Runbook 建议继续按 `LOCAL / TRANSFER / REMOTE / VERIFY / ROLLBACK` 组织，并写明每个逻辑步骤的用途、执行内容和成功条件。

## 阶段 2：由用户确认流程是否稳定

一次成功执行并不自动等于“流程已经成熟”。只有用户明确表示当前 `DEPLOYMENT.md` 已经经过实际使用、整体流程可以固定下来，才进入自动化讨论。

如果用户仍在调整任何步骤，就继续维护 Runbook，不主动把它脚本化。

## 阶段 3：自动化前必须做“使用习惯访谈”

这是 0.8.3 最重要的变化。

**Runbook 中存在某条命令，不代表用户希望脚本执行这条命令。**

Runbook 是完整知识库；一键脚本只是其中一个自动化入口。用户完全可以把某些步骤保留为人工操作、交给其他工具或流程处理、从某个中间阶段开始，或者只在异常时参考某些章节。

因此，在生成脚本前，Agent 必须先对 Runbook 中相关逻辑步骤建立一份“自动化覆盖表”。每个步骤或步骤组至少要明确属于以下一种状态：

- `AUTOMATE`：纳入脚本自动执行；
- `KEEP MANUAL`：继续由用户人工处理；
- `EXTERNAL / HAND-OFF`：由 DSH 之外的其他工具或流程处理；
- `NOT IN NORMAL RUN`：保留在 Runbook 中，但不属于日常一键流程。

同时要确认各阶段之间的交接条件：

- 自动化从什么前提开始；
- 用户会在什么地方人工介入；
- 中间产物是否会被用户选择、调整或处理；
- 自动化在什么条件下可以继续；
- 哪些输入由用户提供；
- 哪些 checkpoint 必须暂停确认；
- 失败时停止、等待人工还是执行既定恢复策略；
- 哪些事情由外部工具或既有流程完成。

这些属于**用户使用偏好和操作习惯**，不能仅靠环境扫描推断。

相反，能够通过只读检查直接确认的事实，不应该重新丢给用户回答。

## 不要假设“完整自动化”就是最优目标

最终脚本不需要覆盖整个 `DEPLOYMENT.md`。

如果用户真实习惯只希望自动化其中几个阶段，那么脚本就只覆盖这些阶段。其余步骤继续留在 Runbook 中作为人工流程、外部交接或恢复手册。

Agent 不应该因为某个步骤已经有现成命令，就默认把它塞进脚本；也不应该为了显得“自动化程度高”而消除用户刻意保留的人工操作。

**自动化边界由用户习惯决定，而不是由 Runbook 章节数量决定。**

## 生成脚本前先回显覆盖表

在真正写 `.ps1`、`.sh` 或其他一键入口之前，Agent 应先向用户回显拟定的自动化边界，例如用结构化摘要说明：

```text
LOCAL        → KEEP MANUAL
TRANSFER     → AUTOMATE
REMOTE       → AUTOMATE
VERIFY       → AUTOMATE
ROLLBACK     → KEEP MANUAL

自动化开始条件：...
人工交接点：...
可变输入：...
失败策略：...
```

这只是格式示意，实际内容必须来自当前项目和用户真实习惯。

用户确认或调整这份覆盖表之后，才能进入脚本生成阶段。

## 阶段 4：脚本来自“已验证 Runbook + 已确认使用习惯”

一键脚本应满足：

- 基于已经验证的 `DEPLOYMENT.md`；
- 只包含用户明确选择自动化的步骤；
- 复用已经验证过的真实命令，不重新发明另一套部署逻辑；
- 只把真正变化的值参数化；
- 保留用户要求的人工 checkpoint；
- 对人工或外部交接后的继续条件做显式检查；
- 明确失败处理和回滚边界；
- 不加入用户未要求的额外自动修改、删除、升级或清理动作。

脚本草案完成后，在保存或运行前仍应展示：

- 文件路径；
- 启动方式；
- 输入参数；
- 自动化覆盖哪些 Runbook 步骤；
- 哪些步骤保持人工或外部处理；
- 人工交接点；
- 失败与回滚策略；
- 完整脚本或足够完整的可审核 diff。

然后让用户选择继续修改、保存但不运行，或保存并试运行。

## DEPLOYMENT.md 始终保留

生成脚本后，`DEPLOYMENT.md` 仍然是人类可读的 source of truth，用于：

- 解释完整部署逻辑；
- 记录环境事实和前提；
- 说明脚本覆盖范围；
- 记录人工和外部交接点；
- 提供脚本失败后的手工恢复路径；
- 在流程变化后指导脚本更新。

如果部署流程或用户的操作习惯发生实质变化，旧脚本应视为可能过期。先更新/验证 Runbook 或自动化覆盖表，再更新脚本。

## 正常部署流程

用户要求部署项目时，Agent 应：

1. 调用 `deployment_runbook_status` 和 `deployment_runbook_read`；
2. 核对 `target-ssh` 与当前会话 SSH lock；
3. 执行只读 Preflight；
4. 展示本次实际执行计划；
5. 获得用户确认；
6. 按 Runbook 执行相应 LOCAL / TRANSFER / REMOTE / VERIFY 步骤；
7. 在逻辑 checkpoint 后读取结果；
8. 按 Runbook 执行验证；
9. 失败时遵守既定边界，不擅自扩大影响面；
10. 当用户明确表示 Runbook 已稳定并希望自动化时，进入使用习惯访谈，而不是直接生成脚本。

## 工具与 UX

- `deployment_runbook_status`：检查当前 Workspace Runbook 状态、hash 和 SSH 目标；
- `deployment_runbook_read`：读取项目自己的 `DEPLOYMENT.md`；
- `deployment_runbook_template`：生成 Runbook 基础结构；
- `deployment_runbook_write`：用户确认后创建/更新 Runbook；
- `ask_user_question`：适合用于 Runbook 审查、成熟度确认、自动化覆盖访谈和脚本确认；
- Harness 原生 approval：用于真正高风险操作的单次授权。

## 最终原则

- **复合命令没问题，隐藏逻辑才是问题。**
- **一键脚本没问题，未经验证就直接一键化才是问题。**
- **Runbook 中有命令，不等于脚本必须执行它。**
- **自动化之前必须先问清楚用户真实的操作习惯。**
- **每个 Runbook 步骤都应先决定：自动、手动、外部交接，还是不属于日常流程。**
- **脚本的边界来自用户习惯，不来自文档结构。**
- **DEPLOYMENT.md 始终保留为完整、可读、可恢复的来源。**
- 高风险操作继续受独立审批保护。
